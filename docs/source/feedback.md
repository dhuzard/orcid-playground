# Help shape the next version

{{ brand }} is a research prototype. **We want scientist-led feedback about actual tasks**, not just a list of imagined features. You do not need to write code.

[Send feedback by email, without GitHub](https://science-record-player.web.app/feedback/) · [Open a GitHub issue](https://github.com/dhuzard/science-record-player/issues/new/choose)

The in-app form prepares an email draft; you still decide whether to send it, or can copy its text. GitHub issues require a GitHub account; using the public app and email feedback route does not.

## A five-minute experiment

Try this with your own public record or the clearly labelled sample data:

| Task | Goal | What to observe |
| --- | --- | --- |
| 1. Explore a profile | Find one publication or affiliation | Does its origin make sense? |
| 2. Run Record check | Identify one actionable improvement | Is the suggested fix valid for your record? |
| 3. Export something | Download a BibTeX, RIS, JSON-LD or Markdown output | Would you reuse it? What is missing? |
| 4. Try My Network | Add or inspect one person/contact and group | What would make this useful in your lab? |
| 5. Open Public Group View | Inspect DOI-based links or an output summary | Do you understand what the relationship does **not** prove? |

You can stop after any task. Please do not share private records, credentials, private contact notes or other researchers' sensitive data in a public issue.

## What feedback is most useful?

Describe **your research role and task** (for example, preparing a grant's team section, following collaborators' outputs, or maintaining a lab website). Then report:

1. What you tried and whether you used real public records or labelled demo data.
2. What you expected, what happened, and where you hesitated.
3. What would make you return to the tool in a month.
4. Which scientific risk or misleading interpretation you noticed.
5. One feature you would prioritize, and what success would look like.

Please distinguish a **bug**, a **scientific limitation** (for example, missing metadata or false relationship inference), and a **feature request**.

## How we will prioritize suggestions

High priority: errors in scientific interpretation, privacy/provenance concerns, and barriers to a reproducible five-minute trial.

Next: repeated, well-defined researcher workflows with evidence that they save work or improve accuracy.

Lower priority: decorative features without an identifiable use case or any unlabelled enrichment that could make the output appear more authoritative than its source.
